# Notes

What broke, what was measured, what surprised me. Newest first.

## Phase 5b: Scale and survive (2026-11-21)
- **Setup:** kind (single node; the Docker VM has 4 GB of the Mac's 8 GB, so Compose and kind don't run together), Calico, KEDA 2.21.1 (Helm), 3 Redpanda brokers with replication factor 3, all services as Deployments. The victim pod carries the collector and enforcer as sidecars: a pod shares one network namespace, which is what Compose emulated with `network_mode: service:victim`.
- **Broke (safety): NetworkPolicies silently not enforced.** kindnet's policy engine needs kernel nfqueue, which fails on OrbStack's kernel (`netlink receive: no such file or directory`), and it fails *open*: a pod reached 1.1.1.1 and the "attacker" reached Redis. Fix: Calico instead of kindnet. Lesson: test that an isolation control actually blocks something; never assume it from "policy created".
- **Broke (my policy design):** NetworkPolicies are additive. The namespace-wide "egress only inside the namespace" policy also selected attacker pods, and its any-pod rule let them reach Redis and Kafka despite the attacker-only policy. Fix: exclude `role=attacker` from the namespace-wide policy. Now: attacker reaches only the victim; nothing reaches the internet.
- **Broke:** once policies were enforced, Prometheus lost all targets: it discovers pods through the API server, outside the namespace. Fix: a narrow egress exception for Prometheus only (ports 443/6443).
- **Broke:** `flow-events` and `features` came up with 1 partition and 1 replica. Kubernetes starts pods in parallel (there's no Compose-style `depends_on`), so the collector published before `redpanda-init` ran, and dev mode auto-created the topics with defaults. That silently kills both scaling (1 partition = 1 useful consumer) and failover (1 replica). Fix: `auto_create_topics_enabled=false` on the brokers; clients retry until the init Job creates the topics. Also: `rpk redpanda start` only accepts `--set key=value` as two arguments; the `=` form is passed through to the broker, which crashes.
- **Bottleneck found by the first load probe (1 replica, 20k events/s, 700 sources):** the feature engine made 3 Redis round trips *per source, sequentially*, at every 1 s tick. With 700 sources a tick took several seconds: 140 vectors/s instead of 700, and the loop fell behind. Fix: all reads for a tick in two pipelined round trips (every source's buckets, then each destination once). See the load test table for before and after.
- **Broke (overload cascade):** the first full load test was meaningless: at 4 replicas the node had 68 MB free, Redis and Postgres probes timed out, and nearly every pod restarted. Strict liveness probes (1 s timeout) killed busy-but-healthy Python processes under CPU saturation, and each restart added a rebalance to the overload. Fixes: lenient liveness (5 s timeout, 6 failures; readiness stays quick); Redpanda `--memory=256M` (each broker had reserved 512 MB up front); Locust scaled to 0 during load tests. The rerun had zero restarts.
- **Chaos run 1 (10 s session timeout):** baseline 3.0 s; kill feature-engine pod 15.7 s; kill detector pod 12.4 s; restart Redis 8.0 s; restart broker 13.9 s. A pod killed abruptly can't leave its group, so its partitions idle until the session timeout evicts it. Lowered to 6 s (the broker minimum) with 2 s heartbeats; librdkafka heartbeats from its own thread, so a busy Python loop can't trigger a false eviction.
- **Broke (dead-broker stall, found by chaos run 2):** a *baseline* attack took 40.3 s, right after the broker-restart scenario. Consumers had fetches in flight to the force-killed broker. Its IP vanished without a TCP reset, so they waited librdkafka's default `socket.timeout.ms` (60 s) and stalled those partitions, including mitigation's. Fix: 10 s socket timeout on every client (fetches long-poll for at most 0.5 s, so 10 s is still generous for a live broker).
- **Broke (harness):** the load generator pods had no `KAFKA_BOOTSTRAP`, fell back to localhost, and `flush()` waited forever, so a whole run produced no load. Fix: pass the address, and bound the flush (fail loudly if anything is undelivered).

## Phase 5a: Observe (2026-11-20)
- **Measured (Gate 5a):** drift alert fired 26 s after shifted traffic arrived; lag alert fired 64 s after the feature engine stopped and resolved 44 s after restart. Both include the 15 s `for:` and 5 s scrape and evaluation intervals; broker lag metrics also update on their own interval.
- **Redpanda v24.2.7 -> v25.1.9** for broker-side consumer-group lag (`enable_consumer_group_metrics`). Broker-side lag keeps reporting when a consumer is dead, which is exactly when it matters; lag computed inside the consumer disappears along with it.
- **Drift: three designs before one worked.** (1) Standard PSI with quantile bins scored *normal* live traffic at 2.3 (alert line 0.25). The training "normal" rows include clients slowed down by HTTP floods in the same session, and Locust is so steady that quantile bins were 0.3 pkt/s wide, so harmless jitter looked like a big shift. (2) A quiet-windows-only reference still gave 1.8. (3) What works: log-scale bins (one per factor of sqrt(2)) and a **one-sided** PSI that only counts bins where live traffic has more mass than training, with a 1/n floor for rare bins. Rationale: models go stale when traffic moves where training was sparse, not when it covers only part of what training saw. Live normal traffic: about 0.05; 1.5x shift: about 9; 20 s of attack in the window: below the alert. Destination features are excluded: every training session contains an attack, so they describe an attacked victim.
- **Bug (found by a unit test):** with tied values (SYN/ACK ratio is almost always 0), `bisect_right` put 0 into the same bin as every positive value, so drift was blind to that feature. Fix: right-closed bins.
- **Broke (classic Prometheus pitfall):** the DeadLetters alert never fired. A labelled counter series is created at its first `inc()`, already at 1, and `increase()` can't see an increase from an unobserved start. Fix: create labelled series at 0 at startup (dead letters, actions, expiries, scored/flagged). The dashboard was also undercounting the first action of each kind.
- **Broke (found by the cold-start regression):** right after Gates 2 and 3 (three floods within about 3 minutes), the drift alert was already firing on normal traffic: attack vectors were ~10% of the 600-vector window. My earlier check only covered one 20 s attack. The real flaw: drift should measure whether *normal* traffic changed (models going stale); attacks are the detector's job. Fix: the drift monitor also reads `scores` and keeps sources flagged in the last 60 s out of the window. A source's first vector can slip in before its score arrives, which is negligible.
- **Broke:** `syn_ack_ratio` drift peaked at 2.6 and decayed over ~2.5 min. Not caused by attacks (normal clients showed zero SYNs through a flood) nor by a feature-engine restart (also zero). It was the drift monitor's **startup**: just after `make up`, Locust clients open their connections (SYNs), and a nearly empty window was dominated by those vectors. Fix: report drift only once the window is full. Lesson: two wrong hypotheses tested and discarded before the timestamp of the service start showed the answer.
- **Known:** each consumer group dead-letters a malformed message independently, so a bad `features` message appears in `features-dlq` twice (detector and drift). The `error` header says why; there's no dedup.
- **Known:** Grafana runs without login: fine on 127.0.0.1 in a lab, not anywhere else.

## Phase 4: Compare (2026-11-20)
- **Dataset:** 28 sessions, 3,323 vectors, about 20 min to generate. Split by session: 13 train (1,514 vectors), 15 test (1,809), with UDP, flash crowds and slow ramps held out of training. Results: `docs/results.md`.
- **Finding: supervised doesn't generalize to new attack types.** XGBoost detected 0% of UDP floods (never seen in training) but 100% of seen types, with 0% false positives even on flash crowds. The threshold detector and the autoencoder caught 100% of UDP floods, because they model "normal" rather than "known attack".
- **Finding: unsupervised can't tell a legitimate surge from an attack.** False positives on flash crowds: threshold 73.6%, autoencoder 100%, XGBoost 0%. A source that is suddenly loud but behaves like a real client looks anomalous to anything trained on normal traffic only. In the live system, that means rate-limiting real users during a flash crowd (seen in a smoke test: client .210 was rate-limited).
- **Finding: the "slow ramp" wasn't hard.** Every detector caught it in the first window, because a SYN-only flood has a huge SYN/ACK ratio at any rate. A genuinely hard ramp would be an HTTP flood with real handshakes ramping slowly. Recorded as a harder attack variant (stretch).
- **Cost:** threshold ~0.5 µs/window, XGBoost ~6 µs, autoencoder ~9-13 µs (1 core, onnxruntime, batch of 1); detector memory ~3 MB vs ~10 MB; model files 0.1 KB vs ~16 KB. All far below the pipeline's rate (a few windows/s per source), so cost doesn't decide this; the error profile does. Throughput varies about 2x run to run on a laptop.
- **Conclusion:** no single winner. XGBoost has the best precision but is blind to new attack types; the baseline is cheap, catches new types, and fails on flash crowds. A sensible production design layers them (e.g. block on XGBoost, rate-limit only on the baseline/autoencoder) or adds flash-crowd features (request success rate, handshake completion).
- **Broke (real bug, found by the live autoencoder check): the victim appeared as a traffic source.** When an attacker's container exits while mitigation still drops its RSTs, the victim retransmits SYN-ACKs to a MAC the bridge no longer knows; the bridge floods them back to the victim, which received its own frames as `PACKET_OTHERHOST`. The collector only skipped `PACKET_OUTGOING`, so it recorded 510 victim-sourced events per attack, and mitigation **rate-limited the victim's own IP** (both the threshold and the autoencoder did, per the audit log). Fix: accept only `PACKET_HOST`. After the fix: 0 of 17,209 events under the same conditions. The dataset was clean (0 victim-sourced rows): mitigation was paused while generating it, so the attacker's RSTs closed every half-open connection.
- **Broke:** importing torch before XGBoost made XGBoost segfault (two OpenMP runtimes on macOS). Then on the real dataset, training deadlocked silently (0% CPU), because torch went multi-threaded. Unit tests with tiny data never hit it. Fixes: import XGBoost first (`ml/__init__.py`); torch single-threaded (the net is tiny).
- **Broke:** Gate 3 judged the whole `actions` table, so earlier runs (smoke tests, the victim bug) failed it. It now only counts rows created during its own run.
- **Changed:** "peak process memory" was ~200 MB for every detector, which was the harness's imports, not the detector. Replaced with memory added by loading and running the detector, plus model size on disk.
- **Live:** Gate 2 passes with all three detectors in the running pipeline (`DETECTOR=...`): detection 1.4-1.6 s. Gate 3 (threshold, refit baseline): rule 3.4-3.7 s, block 8.8-9.1 s, 0 Locust failures.

## Phase 3: Mitigate (2026-11-20)
- **Measured:** time to mitigation (attack launch to first rule) of 3.4 s, 2.3 s and 3.3 s over three runs; block (escalated) at 8.0 s, 7.6 s and 8.0 s. That's detection (~1.5 s) plus 3 consecutive windows, then 5 more for the block. Normal traffic during the attacks: 481, 488 and 515 Locust requests with 0 failures. The allowlisted tester (172.30.0.201) raised 21 alerts and got 0 actions.
- **Design:** the streak is computed from the `alerts` table (unique per source and window), so the controller holds no state and replays are naturally idempotent. Rules are nftables timeout-set members, so the kernel expires them; the controller only records `expired_at`.
- **Design:** the collector taps packets (AF_PACKET) *before* netfilter, so a blocked attacker still shows up in features and keeps being flagged. That's useful: when a rule expires mid-attack, the streak is already past the escalation point and it goes straight back to a block.
- **Security fix (review):** the enforcer API was reachable from the whole lab network, attacker included, so anyone could POST a rule and get legitimate users blocked: our mitigation turned into a DoS against them. Fix: bearer token (`ENFORCER_TOKEN`, constant-time compare; an empty token rejects everything). Gate 3 now probes it from inside the lab and gets 401. The pre-fix images let the same probe through.
- **Broke (measurement):** running Gate 3 right after Gate 2 reported time to mitigation 0.0 s, because Gate 2's block was still active. The gate now waits for any leftover rules to expire before attacking.
- **Known gaps:** if the victim container restarts, its netns (and nft rules) are lost while Postgres still lists them as active; that needs reconcile-on-startup (Phase 5b). Mitigation is per source IP only: a spoofed or distributed flood needs per-destination rate limiting.

## Phase 2: Detect (2026-11-20)
- **Measured:** detection delay (attack launch to first flagged score) of 1.3 s, 1.5 s and 1.3 s over three Gate 2 runs, two of them cold starts. This includes about 1 s of attacker container start-up. 0 false positives in 30 s of normal traffic; only the attacker was ever flagged.
- **Baseline** fitted on 177 vectors from 60 s of normal traffic: bounds pkt_rate 52.6/s, byte_rate 5216.8 B/s, syn_ack_ratio 2.0 (floor). Normal sources run at about 24 pkt/s each. The SYN flood (2000 pps) scores 1.0 immediately.
- **Design:** destination entropy drops for *every* source talking to an attacked destination, so it can't attribute an attack to a source. The baseline scores per-source features only; entropy is kept for the Phase 4 models and for distributed or flash-crowd cases.
- **Exactly-once counting (follow-up fix):** HINCRBY counters alone aren't idempotent, so a crash between the Redis write and the Kafka commit replayed the batch and double-counted it. Fix: the highest counted offset per partition (`fe:offset:{p}`) is written in the same MULTI/EXEC transaction as the counters, and replayed messages at or below it are skipped. This needs one MGET per batch, not per-event IDs. Remaining gap: a zombie replica that still believes it owns a partition after a rebalance could race the new owner. That would need WATCH on the offset key or a fencing token; noted for Phase 5b.
- **Measured (chaos smoke test):** feature engine SIGKILLed then restarted immediately; features resumed after 11 s and 12 s (the 10 s session timeout evicts the dead member, plus ~1 s). After a clean restart, ~1 s. Note: Docker doesn't apply restart policies to `docker kill`, so the test restarts by hand.
- **Gate 2 after the fix:** detection delay 2.0 s.
- **Broke:** after `docker compose restart detector`, no scores arrived for about 45 s. The killed process never left its consumer group, so the rebalance waited out the 45 s default session timeout. Fix: SIGTERM closes consumers (they leave immediately) and flushes producers; session timeout cut to 10 s for real crashes. Recovery after a restart went from about 45 s to about 1 s. This matters for the Phase 5b chaos tests.
- **Broke:** Docker's embedded DNS on `lab` returned SERVFAIL for every name after a failed `make up` (invalid compose file). Identical throwaway networks worked fine, and recreating the stack (`make down && make up`) fixed it. Couldn't reproduce afterwards; if it happens again, recreate first.
- **Broke:** compose `!reset` doesn't apply through a YAML merge (`<<:`). Fix: `networks` moved out of the shared anchor.
- **Review fixes:** the detector now loads the baseline at startup (a missing file fails startup instead of leaving a dead thread behind a 503); the training script exits clearly on zero vectors; renamed a confusing variable; added a named constant in the gate.

## Phase 1: Foundations (2026-11-20)
- Proposal updated (adds §6b on scalability and reliability). Phase 5 is split into 5a/5b/5c. Design rules (no state in memory, at-least-once, idempotent mitigation) now apply from Phase 2 on.
- Decision: per-packet events (not per-flow aggregates). Simplest to parse and lets the feature engine own all windowing. Revisit if Kafka throughput becomes the bottleneck under flood.
- Capture: raw AF_PACKET socket plus a hand-written header parser (no scapy). Fast, no dependency, unit-testable with crafted bytes.
- Broke: the host consumer logged IPv6 connection errors. `localhost` resolved to ::1, but the port is only published on 127.0.0.1. Fix: use 127.0.0.1 everywhere.
- Broke: `scripts/consume.py` printed nothing for 60 s. It used a fixed group id, and killed runs left stale members that the rebalance waited on until the session timeout. Fix: a fresh group id per run.
- Broke (intermittent): Gate 1 sometimes failed on a cold start with UNKNOWN_TOPIC_OR_PART. The topic was only auto-created on the collector's first publish, so a consumer that started earlier failed. It only showed up after a rebuild, when the collector started more slowly. `allow.auto.create.topics` on the consumer did not help (Redpanda doesn't auto-create for consumers); 8 passing runs had hidden this. Reproduced with a no-cache rebuild. Fix: a `redpanda-init` one-shot creates the topic (6 partitions) before the collector starts. Lesson: "passes N times" isn't a fix; reproduce first.
